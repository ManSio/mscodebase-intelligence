# ADR-0001: Threat Model for execute_script sandbox

**Status:** Draft — ожидает решения владельца (OPEN_QUESTION)
**Дата:** 2026-08-05
**Автор:** агент (по итогам внешнего аудита и верификации A2)

## Context

`sandbox/executor.py` честно декларирует в докстринге (executor.py:14):

> NOT a security boundary for untrusted code. Defense-in-depth for agent tools.

Текущая реализация — два слоя защиты:

1. **AST-валидация** (deny-лист): запрещены `eval`/`exec`, `importlib`, `pkgutil`,
   `runpy`, `ast.Delete` (executor.py:73 — «Can delete variables»), опасные
   атрибуты и т.д.
2. **Runtime-перехват**: подмена `__import__` + allowlist модулей + выполнение
   в subprocess с `_build_minimal_env` (executor.py:306), который **намеренно НЕ
   копирует `os.environ`** (executor.py:309: «Deliberately does NOT copy
   os.environ — parent secrets (API keys, ...)» не утекают в дочерний процесс).
   Исключения-минимум: `SYSTEMROOT`, `SYSTEMDRIVE`, `TEMP`, `TMP`.

Внешний аудит (2026-08-05) подтвердил: обвязка сделана аккуратно, но это
классическая blacklist-модель на чистом Python-интерпретаторе **без ОС-изоляции**
(нет seccomp, namespaces, gVisor). История Python sandbox escape
(`object.__subclasses__` цепочки, frame-объекты в трейсбеках исключений,
format-string трюки) показывает, что такие deny-листы со временем протекают.

**Открытый вопрос для владельца:** для какого класса ввода эта defense-in-depth
защита считается достаточной? Есть ли путь, по которому в executor попадает
ввод из внешнего/недоверенного источника (не сгенерированный агентом сниппет
внутри уже доверенного MCP-процесса)?

**Побочное наблюдение (не блокер):** `ast.Delete` блокируется целиком — даже
`del x` для локальной переменной запрещён. Это может быть побочный эффект
широкой формулировки, ломающий легитимный код агента. Если владелец выберет
Вариант A — рассмотреть сужение до `del` глобальных/атрибутных имён.

## Decision

**Рекомендация агента: Вариант A** — сохранить текущую defense-in-depth,
зафиксировать границы модели угроз в этом ADR, **не расширять** поверхность
без нового решения владельца.

Решение финально принимает владелец. До решения `executor.py` не редактируется
(зафиксировано в `.agent_task_state.md` Danger Zone).

## Alternatives considered

### Вариант A: Defense-in-depth (текущий)
- **Применимо:** доверенные сниппеты (генерированные агентом) внутри уже
  доверенного MCP-процесса
- **Guard:** AST-валидация + blacklist + runtime `__import__`-перехват +
  subprocess-изоляция с минимальным env
- **Ограничение:** не защищает от агента-вредителя и от недоверенного внешнего
  ввода (если такой путь появится)
- **Усилия:** 0 (текущее состояние); документирование границ — 1 коммит
- **Риск:** если появится недоверенный источник ввода, blacklist может протечь
  (нужно будет поднять до B)

### Вариант B: OS-изоляция
- **Применимо:** недоверенный ввод (внешний агент, CI-артефакты, пользовательский
  код из репозиториев)
- **Guard:** container/microVM + seccomp (или изолированный runtime)
- **Усилия:** 2-4 недели, новая зависимость, усложнение инсталляции и поддержки
  Windows-платформы (проект активно поддерживает Windows)
- **Ограничение:** в чистом виде избыточно для текущего единственного вызова
  (execute_script → доверенные сниппеты)

### Вариант C: Гибрид
- **Применимо:** оба класса ввода одновременно
- **Guard:** threat classifier на входе: доверенные пути → Вариант A,
  недоверенные → Вариант B
- **Усилия:** выше, чем B (два пути + классификатор)
- **Ограничение:** классификатор сам становится поверхностью атаки (ошибка
  классификации = неверный путь выполнения)

## Impact

- **При Варианте A (рекомендация):** изменения кода нет. Фиксируются границы:
  executor — инструмент для доверенных сниппетов агента, не для пользовательского
  кода. `KNOWN_ISSUES`/README получают явную строку о границах. Новый
  недоверенный путь ввода → немедленное переоткрытие ADR (эскалация до B/C).
- **При Варианте B/C:** новая зависимость, изменения в `install.py`,
  платформенная матрица CI расширяется. Отдельная фича со своим планом.
