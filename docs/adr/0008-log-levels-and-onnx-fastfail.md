# ADR-0008: Уровни логов и быстрый отказ ONNX

**Status:** Accepted
**Дата:** 2026-11-17
**Контекст:** разбор 135 400 строк логов MCP (17 619 WARNING, 368 ERROR)

## Context

Разбор логов показал три вещи, которые не являются ошибками кода, но стоят
времени и внимания:

1. `parser: Giant function chunked` — **5 509** записей WARNING за неделю.
   Это штатное дробление больших функций при индексации, а не сбой.
2. `project_resolution: CWD не похож на проект` — **3 203** записи WARNING.
   Хост запускает сервер из каталога расширения, поэтому подмена
   `CWD → PROJECT_PATH` повторяется на каждом вызове инструмента.
3. `[ONNX Client] Сервер не поднялся за 60s` — **146** записей WARNING и
   соответствующее время ожидания. Причина: в worktree нет каталога
   `.codebase_models/onnx/<model>`, сервер падает через ~0.1 с, а клиент
   всё равно ждёт `_wait_for_server(timeout=60)`.

Вторая находка того же разбора — `Artifact migration SKIPPED … WinError 123`
(**1 100** записей): миграция legacy-артефактов не воспроизводится на чистом
проекте (проверено), поэтому чинить её по догадке нельзя.

## Decision

1. **`Giant function chunked` → INFO.** WARNING остаётся для аномалий; признак
   «функция больше `MAX_CHUNK_CHARS`» — ожидаемое свойство корпуса.
2. **Подмена CWD предупреждает один раз на пару `(cwd, PROJECT_PATH)`,** дальше
   DEBUG. Сигнал не теряется (первый раз в логе), но 3 203 строки не топят
   остальное; в одном процессе пара обычно одна.
3. **Клиент ONNX проверяет наличие каталога модели до запуска процесса** и
   отказывает сразу, называя все места поиска. Резолвер вынесен в
   `src/core/embedder/model_paths.py` — один список для сервера и клиента
   (раньше сервер искал в трёх местах, клиент об этом не знал).
4. **Миграция артефактов: поведение не меняется.** Добавлена только диагностика
   (`src=`/`dst=` в предупреждении). Правка без воспроизведения запрещена
   протоколом.
5. **Read-only режим второго сервера: поведение не меняется.** Проверено по
   коду: запись идёт через `db_manager.begin_write()`, который при чужом
   PID-lock бросает `RuntimeError` с явным текстом («база занята другим
   процессом MCP»), то есть отказ громкий, а не тихий. Причина помечена в
   health как issue.

## Consequences

- В логах одинаковый сценарий даёт **0** WARNING вместо 7 (замер: один
  `search_code` на temp-проекте, до/после).
- Отказ эмбеддинга без модели — **2 с** вместо **60 с** ожидания (замер:
  с откатом guard'а тест `test_missing_model_fails_fast` занимает 64.65 с и
  падает, потому что клиент честно ждёт `_wait_for_server`).
- Ни один сигнал не удалён: giant-function виден на INFO, подмена CWD — первым
  WARNING, отсутствие модели — ERROR со списком путей.
- Риск «спрятали настоящую проблему»: снят тем, что первый WARNING остаётся, а у
  ONNX-отказа появился явный ERROR с причиной вместо таймаута.

## Alternatives rejected

- **Понизить оба сигнала до DEBUG** — теряется диагностика конфигурации.
- **Убрать ожидание ONNX совсем** — модель может появиться позже (скачивание);
  проверяем только отсутствие каталога, а не «сервер не поднялся».
- **Чинить миграцию по гипотезе** — `WinError 123` не воспроизвёлся ни на
  чистом проекте, ни в матрице условий (dst-файл → 183, symlink → 3,
  длинный путь → OK, `CON` → OK). Нужен реальный `src/dst` из нового лога.
- **Менять read-only режим** — он защищает от двух писателей; отказ уже
  fail-closed и с понятным текстом.
